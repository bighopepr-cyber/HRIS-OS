# CLAUDE.md

Berkas ini menyediakan panduan bagi Claude Code (claude.ai/code) saat bekerja dengan kode di repositori ini.

## Gambaran umum proyek

HRISINDO: perangkat lunak HR open-source untuk tim yang bertumbuh (orang dan departemen, orientasi khusus undangan, absensi, cuti dan hari libur, penggajian dan slip gaji, kinerja, penggantian biaya, aset, laporan). Berlisensi AGPL-3.0. Awalnya dibangun (scaffolded) melalui Lovable; sebuah SPA Vite + React + TypeScript dengan dukungan Supabase (Postgres + Auth + Storage + Edge Functions). Setiap deployment adalah **ruang kerja satu perusahaan**; tidak ada multi-tenancy.

## Perintah

- `npm run dev`: dev server Vite pada port 9002.
- `npm run build`: build produksi ke `dist/` (Vite tidak melakukan typecheck).
- `npm run lint`: ESLint.
- `npm run typecheck`: `tsc` untuk aplikasi dan konfigurasi node.
- `npm test`: unit test Vitest (`src/**/*.test.ts`).
- `supabase/tests/run.sh`: pengujian database (`permissions.test.sql`) terhadap Postgres biasa, menggunakan `supabase_stub.sql` sebagai pengganti skema `auth`/`storage` milik Supabase. Atur `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`.

CI (`.github/workflows/ci.yml`) menjalankan lint, typecheck, unit test, pengujian database, dan sebuah build; `check-migrations.yml` menolak migrasi baru yang mengandung `USING (true)`.

Supabase CLI mengelola migrasi dan fungsi untuk proyek yang tertaut (`npx supabase link --project-ref <ref>`; deployment upstream adalah `ppdsxgkmnmjfwmpnamts`). Migrasi berada di `supabase/migrations/` (berawalan timestamp, hanya boleh ditambahkan); edge function di `supabase/functions/<name>/index.ts` dengan helper bersama di `_shared/`. Langkah self-hosting ada di `docs/self-hosting.md`; secret fungsi di `supabase/functions/.env.example`; variabel frontend di `.env.example`.

## Arsitektur

**Routing (`src/App.tsx`)**: rute pemasaran publik (`/`, `/features`, `/how-it-works`, `/pricing`, `/security`, halaman legal, `/auth`, `/reset-password`) dan rute aplikasi yang dibungkus `ProtectedRoute` + `DashboardLayout`. Status autentikasi berasal dari `useAuth()` (`src/contexts/AuthContext.tsx`). `ProtectedRoute` menampilkan status "not available yet" di dalam shell kepada orang yang diundang tetapi tidak tertaut ke data karyawan dan tidak memiliki akses modul apa pun; `DashboardLayout` menyembunyikan modul yang tidak bisa mereka gunakan.

**Lapisan data**: seluruh akses data dilakukan melalui Supabase client (`src/integrations/supabase/client.ts`, hasil generate; `types.ts` memuat tipe DB). TanStack Query untuk pengambilan data dan mutasi, berada di `src/hooks/use*.ts`. Kode sisi klien berkomunikasi dengan Postgres secara langsung lewat PostgREST; RLS menentukan apa yang dapat dilihat oleh setiap permintaan. Saat meng-embed sebuah tabel yang memiliki lebih dari satu foreign key ke target yang sama (misalnya `employees` → `departments`, atau `employees` → `employees` untuk manajer), beri nama relasinya (`departments!employees_department_id_fkey(...)`) atau embed melalui kolom FK (`manager:manager_id(...)`); embed tanpa kualifikasi akan gagal dengan PGRST201.

**Model izin** (`20261003100000_module_permissions.sql`):
- Peran (`app_role`: `admin`, `hr`, `manager`, `employee`) berada di `user_roles`. `role_permissions` memberi setiap peran sebuah tingkat (`view` < `manage`) per modul (`app_module`: employees, onboarding, attendance, leaves, reimbursements, performance, assets, payroll, calendar, settings). `user_permissions` memberi satu orang akses tambahan di atasnya.
- Helper SQL yang digunakan dalam policy: `can(module, level)`, `is_admin()`, `has_any_module_access()`, `is_active_member()`, `is_not_blocked()`, ditambah `get_my_employee_id()` dan `is_manager_of(employee_id)` untuk baris milik sendiri dan milik tim. `get_my_permissions()` mengembalikan tingkat efektif pemanggil sebagai JSON untuk UI. Khusus service role: `user_can(user_id, module, level)` dan `users_with_module_access(module, level)` (dipakai oleh edge function untuk memilih penerima notifikasi).
- Frontend: `usePermissions()` (`src/hooks/usePermissions.ts`) dan `hasModuleAccess()` / `canAccessSettings()` (`src/lib/permissions.ts`) mencerminkan kondisi database untuk menampilkan dan menyembunyikan UI. Keduanya tidak pernah memberi akses secara mandiri.
- Sebuah trigger mencegah penghapusan admin terakhir.

**Akun khusus undangan dan orientasi** (`20261003100100_invite_only_accounts.sql`, `20261006100000_onboarding_invites.sql`): HR menambahkan karyawan baru di **Onboarding**, yang menyisipkan baris `employees` (status `onboarding`) dan memanggil fungsi `invite-employee`. Fungsi tersebut membuat atau memakai ulang baris `user_invitations` untuk karyawan itu (`employee_id`, `last_sent_at`, `send_count`) dan mengirim email berisi tautan pendaftaran (Supabase `generateLink`, dikirim melalui Resend; `inviteUserByEmail` ketika Resend belum dikonfigurasi) yang menuju `/reset-password?welcome=1` untuk memilih kata sandi. Trigger `BEFORE INSERT` pada `auth.users` (`enforce_invite_only_signup`) menolak akun tanpa undangan yang masih terbuka; `handle_new_user` menetapkan peran yang diundang, mengisi `accepted_user_id`, dan menautkan data karyawan. Undangan baru dianggap *diterima* ketika orang tersebut mengonfirmasi / masuk untuk pertama kali (`on_auth_user_activated` → `complete_invitation()`), yang juga memindahkan karyawan ke status `active` dan memberi tahu pengundang. Saldo cuti dibuat oleh trigger setiap kali seorang karyawan menjadi aktif. `invite-employee` juga membatalkan undangan (mencabut dan menghapus akun yang belum pernah terpakai). Domain email dapat dibatasi melalui pengaturan organisasi `domain_whitelist`, yang ditegakkan di database. Permintaan orientasi mandiri yang lama (`onboarding_requests`) tidak lagi dipakai oleh aplikasi.

**Offboarding** (`20261008100000_offboarding.sql`): `employee_exits` (alasan, tanggal pemberitahuan, hari kerja terakhir; status `requested` → `in_progress` → `completed`, atau `declined`/`cancelled`) beserta checklist-nya `exit_tasks`. HR memulai satu dari baris karyawan (Start offboarding); seorang karyawan mundur dari profilnya dan seseorang dengan `onboarding:manage` menyetujuinya (`guard_employee_exit`: tidak ada persetujuan atas diri sendiri, admin tunggal tidak dapat di-offboard). HR memilih siapa yang menerima checklist offboarding per departemen (kunci `organization_settings` `offboarding_checklist`, dapat disunting oleh `onboarding:manage`) ketika memulai atau menyetujui: karyawan (`notify_employee_ids`) dan alamat di luar (`notify_emails`), ditambah sebuah catatan; fungsi `offboarding-email` mengirimkannya lewat email (balasan diteruskan ke pengirim) dan `offboarding-reminders` (pg_cron, 09:00 IST) mengirim ulang pada hari kerja terakhir. Pengunduran diri meng-email HR dan manajer pelaporan, dengan konfirmasi kepada karyawan; persetujuan dan penolakan meng-email karyawan. Tim mengonfirmasi dengan membalas; `exit_tasks` tidak lagi digunakan. Berstatus `in_progress` akan menetapkan `employees.exit_date` ke hari kerja terakhir yang direncanakan; penggajian menghitung prorata bulan terakhir berdasarkan nilai tersebut dan melewati orang yang sudah pergi sebelum bulan itu. `process_employee_exits()` (pg_cron, harian) memanggil `complete_employee_exit()` pada hari setelah hari kerja terakhir: status `offboarded`, akses masuk diblokir, cuti yang tertunda dibatalkan. Status karyawan ditentukan oleh alur kerja (`guard_employee_status`): pengguna akhir hanya dapat memindahkan onboarding → active; `inactive` tidak lagi digunakan. Fungsi SECURITY DEFINER yang harus melewati proteksi pengguna akhir menetapkan setelan `peoplo.system_action` tingkat transaksi, yang dihormati oleh `is_end_user_request()`.

**Revisi gaji** (`20261011100000_salary_revisions.sql`): setelah baris `salary_structures` yang awal, perubahan gaji hanya dapat dilakukan melalui `salary_revisions` (tipe, `effective_from`, alasan, `performance_review_id` opsional, tujuh komponen, snapshot `previous`, `notify_employee`); `guard_salary_structure` memblokir pembaruan oleh pengguna akhir, serta penyisipan/penghapusan gaji milik sendiri oleh non-admin. `guard_salary_revision`: hanya payroll manage, tidak boleh gaji sendiri kecuali admin, status `pending_approval` bila `organization_settings` `salary_revision_approval` diaktifkan (khusus admin, `guard_salary_revision_approval_setting`), jika tidak `scheduled`; persetujuan/penolakan tidak boleh dilakukan oleh pengusul maupun pihak yang bersangkutan; revisi tidak dapat disunting, hanya dapat dibatalkan. `apply_salary_revision()` berjalan ketika tanggal sebuah revisi yang dijadwalkan telah tiba (saat penyisipan/persetujuan, atau `apply_due_salary_revisions()` melalui fungsi harian `salary-revisions`, yang juga meng-email karyawan): fungsi ini memperbarui struktur (baris riwayat dengan alasan dan pelaku), serta mencatat `adjustment_amount`: tunggakan untuk bulan-bulan yang sudah masuk payroll, atau prorata negatif untuk bulan yang belum dijalankan dan dimulai di tengah jalan. `attach_salary_adjustments` menambahkan penyesuaian yang belum terlampir ke penyisipan `payroll_records` berikutnya (`adjustment_amount`/`adjustment_note`, ikut dihitung dalam `net_salary`). `payroll_records` menyimpan komponen yang dipakai untuk menghitungnya (`hra` … `pf_deduction`; null pada baris lama, yang slip gajinya memakai struktur sebagai cadangan melalui `payslipComponents()`). UI: `SalaryRevisionsPanel`/`SalaryRevisionDialog` (`src/components/payroll/`), `useSalaryRevisions.ts`, surat PDF di `src/lib/salaryRevisionLetter.ts`.

**RLS** (`20261003100200_rls_module_permissions.sql`, `20261003100250_storage_policies.sql`): policy setiap tabel didefinisikan di satu tempat di atas model izin, ditambah policy restriktif `"Deny blocked users"` untuk setiap tabel dan pada `storage.objects`. `employee_directory` adalah view yang hanya mengekspos kolom aman kepada anggota aktif.

**Penjaga integritas** (`20261003100300_integrity_guards.sql`): trigger yang hanya berlaku untuk permintaan pengguna akhir (`is_end_user_request()`, sehingga service role dan SQL editor tidak terpengaruh) dan melewati orang-orang dengan akses `manage`: permintaan cuti dan penggantian biaya selalu dimulai sebagai `pending` dan hanya pemberi persetujuan yang dapat mengubah statusnya; absensi tidak dapat dicatat mundur (backdate) atau disunting setelah clock-out; penilaian KPI/tujuan hanya dapat dilakukan oleh pemiliknya (`guard_rating_ownership`); pengakuan tinjauan kinerja dan path dokumen orientasi diperiksa. Data rekening bank disimpan di `employee_bank_details`, bukan `employees`.

**Edge function** (Deno): notifikasi yang dipicu pengguna (`leave-*`, `reimbursement-*`, `review-*`, `onboarding-notification`), `invite-employee` (kirim / kirim ulang / batalkan undangan), `offboarding-email` (email checklist, pengunduran diri, dan keputusan), `salary-revisions` (email revisi dari aplikasi; harian: terapkan revisi yang jatuh tempo dan kirim email), `send-push-notification` (web push, VAPID), `version-check` (rilis GitHub), serta yang terjadwal `attendance-reminders`, `goal-reminders`, `onboarding-reminders`, `offboarding-reminders`, `event-notification`, `generate-monthly-payroll`. Helper bersama di `_shared/`: `authenticateCaller()` (memverifikasi JWT, menolak pengguna yang diblokir, mengembalikan klien service role), `userCan()`, `usersWithModuleAccess()`, `getEmployeeIdForUser()` (`auth.ts`); `corsHeaders`/`jsonResponse` (`cors.ts`); `escapeHtml` (`html.ts`); `verifyCronSecret()` (`secrets.ts`, pemeriksaan waktu konstan atas header `x-cron-secret` dibandingkan `CRON_SECRET`). Fungsi yang ditandai `verify_jwt = false` di `supabase/config.toml` harus melakukan autentikasi pemanggil sendiri. Email dikirim melalui Resend (`RESEND_API_KEY`, `RESEND_FROM_EMAIL`); tautan memakai `APP_URL`.

**Tumpukan UI**: shadcn/ui (`src/components/ui/`) di atas Radix, Tailwind (`tailwind.config.ts`, token di `src/index.css`), `lucide-react`. Komponen fitur per modul berada di bawah `src/components/<module>/`. Halaman pemasaran berbagi `PublicHeader`, `Footer`, `PublicCtaSection` (`src/components/layout/`) serta komponen 3D/motion berbasis CSS di `src/components/landing/` (hormati `prefers-reduced-motion` melalui `motion-decor`). URL publik (repo, lisensi, panduan) berasal dari `src/lib/site.ts` (`VITE_REPO_URL` meng-override repo).

**Konvensi desain**: Inter; warna utama `hsl(201 96% 32%)` (`#0369a1`); `muted-foreground` adalah abu-abu sedang untuk teks sekunder. Mata uang adalah ₹ dengan format `en-IN`; tanggal `MMM d, yyyy` (date-fns, parsing string `yyyy-MM-dd` dengan `parseISO`, jangan pernah `new Date(str)`). Lencana status melalui `statusBadgeClass()` / `formatStatus()` / `pluralizeDays()` (`src/lib/statusStyles.ts`). Setiap layar harus berfungsi pada 390px: tabel berubah menjadi kartu di bawah `sm`, aksi dialog diletakkan di `DialogFooter` (lengket di mobile), tombol khusus ikon memerlukan `aria-label`. PWA lewat `vite-plugin-pwa` dengan `public/sw-push.js` untuk push.

## Konvensi keamanan

- Tabel baru dikirim dengan RLS dalam migrasi yang sama: policy restriktif `"Deny blocked users"` dan policy yang dibangun di atas `can()`, `get_my_employee_id()` dan `is_manager_of()`. Jangan pernah memakai `USING (true)` tanpa komentar dan tinjauan eksplisit.
- Menambahkan modul atau tingkat izin berarti memperbarui enum `app_module`, default `role_permissions`, `src/lib/permissions.ts` (`MODULES`), dan `supabase/tests/permissions.test.sql` secara bersamaan.
- Alur kerja dengan persetujuan atau dampak finansial memperoleh trigger penjaga (ikuti pola fungsi `guard_*`) dan sebuah pengujian database.
- Edge function: tangani `OPTIONS`, lakukan autentikasi dengan `authenticateCaller()` atau `verifyCronSecret()`, periksa `userCan()`, muat record berdasarkan id dari database alih-alih mempercayai body permintaan, pilih penerima di sisi server, dan escape semua yang ada di email HTML.
- Jangan pernah mengekspos service role key ke browser. Jangan pernah meng-interpolasi input pengguna ke dalam SQL di migrasi atau RPC.
- Jaga agar tautan **Source code** di dalam aplikasi (AGPL-3.0 §13) tetap berfungsi.
